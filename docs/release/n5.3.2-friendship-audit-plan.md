# N5.3.2 — Friendship, notifications and direct friend chat

Status: approved incremental implementation plan. The existing N6 maintenance and realtime-scaling epic remains unchanged.

## Current-state map

| Capability | Current behavior | Main gaps |
| --- | --- | --- |
| Friendship storage | `friendships` stores two directed rows per accepted relationship. The API lists one direction and deletion removes both directions. | No canonical pair row; delete is not explicitly transactional or audited; a partial pair is representable. |
| Friend requests | Slice 1 uses opaque `frq_` IDs; incoming/outgoing list, create, accept, decline and cancel are owner-scoped. Mutations lock both accounts in deterministic order, revalidate active/verified/ban/block state and emit minimized realtime invalidations only after commit. Duplicate and concurrent terminal actions are idempotent. | Directed friendship rows remain until the friend-list slice treats the pair as one transactional aggregate. Request expiry is intentionally reserved for chat requests. |
| Friend list | Slice 2 returns only public-ID cursors plus server-derived capabilities, renders explicit accessible row menus and provides loading/empty/error states. Remove and block lock the account pair, delete both directed friendship rows and cancel pending friend/chat requests atomically and idempotently. | Coarse online display and realtime invalidation still use process-local presence until N6 distributes realtime state; neither is trusted for authorization. |
| Chat requests | Pending requests persist in PostgreSQL and are listed only to the receiver. The UI section is hidden when empty. | Creation/acceptance is split across non-transactional queries; requests do not expire; no canonical unordered-pair conflict handling; database IDs are used by Socket.IO. |
| Direct friend chat | Server verifies account, verified email and friendship before creating a request. Accepting can pair two locally present, unpaired sockets and creates a `direct` conversation. | Presence, active pairs and delivery are process-local. Acceptance temporarily flips DB state and may revert it. Concurrent accepts/multi-tab can race. Direct and random conversations share the same client lifecycle, so Next/rematch semantics are not explicitly separated. |
| Notifications | Account and guest notifications persist, support cursor pagination and idempotent read marking. Account-ban records are excluded from the product feed. | No user delete/dismiss lifecycle. Notification payloads and request IDs are not governed by a versioned public contract. Some realtime emits happen before transaction commit. |
| Conversation menus | Random chat has server-gated Add friend, Report, Save and Next behavior. | Capabilities are assembled ad hoc. No distinct friend/direct context menu or server-authoritative action matrix. |
| Privacy and audit | Public principal IDs are returned for people. Safe logging avoids message content and raw network/device signals. | Social mutations have no consistent audit policy; database sequence request IDs are exposed; online state can reveal presence more broadly than needed. |

## Proposed data and lifecycle model

### Identity and public contracts

- Keep numeric database keys internal. Add stable, opaque public IDs for friend requests, chat requests and notifications; accept only those IDs at HTTP and Socket.IO boundaries.
- Return server-derived capabilities such as `canMessage`, `canRemoveFriend`, `canBlock`, `canReport` and `canAddFriend`. Never accept roles, friendship, presence, ban state or conversation type from the browser.
- Use generic unavailable/conflict feedback. Do not reveal blocks, moderation signals, exact presence, queue internals or anti-abuse thresholds.

### Friendship lifecycle

- Prefer one canonical unordered friendship row, with `(lower_user_id, higher_user_id)` uniqueness and timestamps. If directed rows must remain for compatibility, add transactional integrity checks and treat the pair as one aggregate.
- Give pending friend requests a canonical unordered-pair uniqueness rule, public ID, terminal timestamps and optional expiry/cancellation fields.
- Create, accept, decline, cancel, remove and block within transactions that lock the canonical pair in deterministic order. Revalidate active users, verification, blocks and existing relationship state before every transition.
- Make repeated requests and responses idempotent. Emit realtime events only after commit; clients reconcile by refetching authoritative state.

### Chat-request and direct-conversation lifecycle

- Persist chat requests with a public ID, status, created/expiry/responded timestamps and one active request per unordered friendship pair.
- Treat `pending -> accepted|declined|cancelled|expired` as a compare-and-set transition. Acceptance reserves both principals atomically before creating one direct conversation.
- Keep direct-chat semantics distinct from random matching: direct chat has End conversation and return-to-friends behavior; it never invokes Next, skip counters or the random queue.
- Store conversation type server-side and return a minimal lifecycle/capability payload with every match. Reconnect may restore only a server-owned active conversation; it must not accept a client-provided identity or conversation owner.
- Move presence, reservations, request delivery and active-pair routing to the shared realtime layer planned by the existing maintenance/scaling epic before claiming cross-replica direct chat support.

### Notifications

- Define versioned notification types with minimal payloads containing public IDs only.
- Add idempotent read and user-dismiss/delete transitions. Prefer `dismissed_at` for predictable sync and retention cleanup; never allow product deletion to remove security/audit records.
- Insert notifications in the same transaction as the source mutation, then publish a content-free invalidation event after commit.

### Audit and privacy

- Audit only sensitive relationship transitions that need accountability: action, actor/target internal references, result, timestamp and correlation ID. Do not copy chat messages, raw IPs, fingerprints or free-form client data.
- Do not audit ordinary reads, presence polling or message bodies. Keep report evidence in the existing controlled report path.
- Rate-limit friend/chat request creation and response events by server principal with distributed counters; return only a generic `retryAfter`.

## Ordered vertical slices

1. **Contract and schema foundation** — settle numbering, add public IDs/status constraints/canonical pair invariants and backfill safely; document API/Socket contracts and rollback compatibility.
2. **Friend-request lifecycle** — transactional create/accept/decline/cancel, post-commit invalidation, idempotency, block revalidation and cross-replica integration tests.
3. **Friend list and menus** — server capability payloads, accessible friend-row/context menus, remove/block confirmation and empty/loading/error states.
4. **Notifications lifecycle** — versioned payloads, appearance/read/dismiss/delete behavior, retention and multi-tab reconciliation.
5. **Chat-request lifecycle** — durable expiry, idempotent send/respond/cancel, generic feedback, distributed limits and authoritative request status.
6. **Direct friend chat** — reserve participants, create exactly one `direct` conversation, separate End behavior from random Next/skip, reconnect rules and server-owned context menus.
7. **Distributed realtime hardening** — shared adapter/presence/reservations, cross-replica delivery and failover tests; coordinate with the existing realtime-scaling roadmap.
8. **Mobile/accessibility polish and rollout** — `390x844`, keyboard/safe-area, drawers/modals/menus, staged flags, metrics without sensitive data and rollback rehearsal.

Each slice should ship schema/server/client compatibility in that order, with targeted tests and a separately reviewable commit or PR.

## Security, concurrency and privacy risks

- Pair symmetry can split under concurrent accept/remove/block unless all transitions lock the same canonical key.
- Multi-tab or cross-replica responses can create duplicate direct conversations without a database-backed reservation/idempotency constraint.
- Publishing before commit can show actions that later roll back; all notifications should be outbox-style or post-commit invalidations.
- Process-local presence can route to a stale socket or leak misleading online state. Return coarse capability/availability and tolerate refetch.
- Request enumeration is possible while numeric IDs are public. Public opaque IDs plus owner-scoped queries are required.
- Block and ban changes must win races with request acceptance and conversation creation.
- Direct conversations must never inherit random Next/skip or silently enqueue either participant.
- Notification JSON can become a privacy escape hatch; validate per-type schemas and allow only public identifiers and fixed metadata.
- Audit/logging must exclude message text, raw IP, device fingerprints and client-provided diagnostic blobs.

## Acceptance and test matrix

| Area | Acceptance criteria | Required tests |
| --- | --- | --- |
| Friend requests | Create is authorized, verified, block-aware and idempotent; accept creates one relationship; decline/cancel are terminal and owner-scoped. | Unit validation; PostgreSQL concurrent create/accept/block races; HTTP CSRF/auth/IDOR; cross-replica retry. |
| Friend list | Only current relationships appear; public IDs only; actions come from server capabilities; empty/loading/error states are accessible. | Integration pagination/privacy; Playwright keyboard/menu/focus; `390x844`, tablet and desktop. |
| Friendship removal/block | One transaction removes the full relationship; repeated calls are harmless; pending/direct requests cannot revive it. | PostgreSQL rollback/concurrency; Socket disconnect/invalidation; audit metadata privacy. |
| Chat requests | One active request per pair; send/respond/cancel/expiry are idempotent; generic cooldown feedback; no presence or block disclosure. | Unit state machine; distributed limiter; multi-tab/cross-replica Socket.IO; expiry integration. |
| Direct friend chat | Exactly one `direct` conversation; both parties authorized at creation; End never enqueues random matching; reconnect follows server state. | PostgreSQL reservation race; Socket concurrent accepts/disconnect/reconnect; browser lifecycle. |
| Random chat isolation | Random Next and progressive skip policy are unchanged; direct flows cannot bypass queue or message limits. | Regression Socket.IO and browser suites, including N5.2 cross-replica cases. |
| Notifications | Source mutation and notification commit together; list appears, read is idempotent, dismiss/delete is owner-scoped and retention-safe. | Transaction rollback; HTTP IDOR/CSRF; realtime-after-commit; multi-tab UI. |
| Menus | Friend-list and conversation context menus expose only server-authorized actions, use Lucide icons, 44px targets, visible focus and AA contrast. | Contract tests plus Playwright keyboard, pointer, escape/outside-click and responsive screenshots. |
| Privacy/audit | No internal/publicly unsafe IDs, message bodies, raw IPs or fingerprints in client payloads, logs or audit rows. | Static privacy checks; captured payload assertions; safe-log/audit integration tests. |
| Rollout/rollback | Backward-compatible migrations, feature flags and mixed-version behavior are documented; rollback does not orphan active relationships or conversations. | Migration up/compatibility rehearsal, old/new server contract tests, staging smoke and rollback drill. |

## Slice gates

Before each N5.3.2 commit, complete targeted tests and report changes, residual risk, staging checks and rollback. Keep friendship requests, friend-list UI, notifications, chat requests and direct-chat lifecycle as separate reviewable slices. N6 remains the prerequisite roadmap for full cross-replica presence and active-pair routing; N5.3.2 must fail safely until that shared realtime layer exists.
